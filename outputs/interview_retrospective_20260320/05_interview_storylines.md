# 核心叙事与常见追问

## 90 秒版本

以下为核心叙事段落：

> 这个项目里我一开始做了很多轮 SFT 和 DPO，但早期结论其实都不成立。最早的问题不是模型本身，而是三件事同时有问题：数据分布不对，训练有数值不稳定，评测链路也会 parse fail。
> 后来我把问题拆开了。SFT 只做低风险流程能力，比如简单推荐和多轮 followup；DPO 只做真实客服偏好，比如促单、安抚、需求对齐，不再拿它补基础能力。
> 同时我把 benchmark 从看整体平均分，改成只看 base 明显失败的子集，再给 DPO 加 hard gate 和更强 judge。
> 最后 SFT 在 4 个 failure-first 场景里赢了 3 个，最佳版本是 `0.7156 vs 0.4531`；DPO 在 5 个真实客服场景里赢了 3 个，最佳版本是 `0.5595 vs 0.4572`。
> 但我没有把它说成"全面替代 base"，因为高风险转品和议价场景依然保留了 manual review。这也是我觉得这个项目最像真实工程的地方。

## 3 分钟版本

### 1. 先说最初为什么失败

- 最早的混合 SFT / DPO 结果里，base 明显更稳
- 有些 SFT / DPO 输出甚至生成了与中文电商场景无关的英文商品文本
- 训练日志里出现 `nan` 和异常 loss
- 早期 benchmark 里还有 `judge_parse_failed`

### 2. 再说关键转向

- 把整体平均分目标改成 `failure-first`
- 只挑 `base < 0.5` 的 case 做 SFT / DPO
- 明确任务边界：
- `SFT` 只做 simple recommendation 和 followup memory
- `DPO` 只做真实客服偏好，不再补 direct answer 或 refusal 这种基础能力
- 给 DPO 加 business gate 和更强 judge

### 3. 最后说结果和边界

- SFT 最终在 4 个 targeted 场景里赢 3 个
- DPO 最终在 5 个 realistic-service 场景里赢 3 个
- 但高风险场景没有放开，仍然路由人工
- 所以这个项目的价值不是"全量替换 base"，而是"明确了怎么把小模型用在它真正能赢的局部场景里"

## 常见追问与应答

### 问：为什么前面做了那么多轮都失败？

答法：

> 因为前面我把几类问题混在一起了。数据分布、训练稳定性、评测稳定性、任务方法匹配，这四件事只要有一件没做好，结果看起来就像模型不行。后来我逐层拆开，才知道真正的问题在哪。

### 问：为什么 SFT 最后能赢？

答法：

> 因为我不再让 SFT 解决所有问题，只让它解决自己最擅长的流程型能力问题，比如简单推荐和 followup memory。而且训练数据只保留 failure case 对应的品类和任务，不再混入其他分布。

### 问：为什么 DPO 前面失败、后面又成功了？

答法：

> 前面失败是因为我让 DPO 去补基础能力，比如 direct answer、拒答边界、prompt echo，这不是 DPO 的强项。后面成功是因为我把它改成真实客服偏好校准，只在模型已经会答的前提上优化服务感、说服力和需求对齐。

### 问：为什么不直接说"DPO 全面优于 base"？

答法：

> 因为真实工程里不该这么说。DPO 在 pairwise 上可以更像客服，但业务正确性不一定已经足够，所以最后仍有 2 个场景必须 manual review。我觉得这比强行全自动更专业。

### 问：这项目里最重要的工程经验是什么？

答法：

> 不是"多训几轮"，而是先把任务边界、数据边界、评测边界讲清楚。对小模型来说，正确拆题比一味调参更重要。

## 核心亮点总结

- 项目不是只看 benchmark 均值，而是把 case-level routing 做成了主结论，避免把局部提升误判成全量可替代。
- 项目明确区分了 `SFT=流程能力修复` 和 `DPO=真实客服偏好校准`，这让实验从无方法论指导的试错变成了有方法论的迭代。
- 项目将 `manual_review` 保留在高风险场景里，说明最终收敛成了一个可上线思维的路由方案，而不是纯离线分数游戏。
