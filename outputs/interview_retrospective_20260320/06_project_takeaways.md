# 项目心得

## 1. "优于 base" 必须带限定语

本项目最容易被追问的点，就是项目是否实现了对 base 的全面超越。

更准确的说法应该是：

- SFT 在 `failure-first` 的低风险流程场景里，部分优于 base
- DPO 在 `realistic-service` 的真实客服偏好场景里，部分优于 base
- base 仍然是很多低风险泛化场景里最稳、最快、最值得默认走的模型

这不是保守，而是严谨。

## 2. benchmark 设计本身就是项目的一半

本项目中最重要的转折，不是某次训练参数变化，而是 benchmark 口径变化：

- 从看整体平均分
- 到看结构化局部场景
- 再到看 `base < 0.5` 的 failure-first 子集
- 最后到真实客服业务流 benchmark

如果 benchmark 不贴业务，模型再高分也没有复盘价值。

## 3. 训练、数据、评测要分层排障

本项目最大的收获之一，不是"一次训成"，而是最终形成了清晰的排障顺序：

1. 先看训练稳定性，有没有 `nan`
2. 再看数据边界，有没有混入错误分布
3. 再看评测链路，有没有 parser / judge 问题
4. 最后才看模型方法本身是否适合这个问题

这个顺序更接近真实工程实践，而不是无方法论指导的试错。

## 4. 小模型对齐不是"全自动替代"，而是"局部场景专用化"

最后真正经得起复验的项目价值，不是：

- "3B 小模型全面追平 base"

而是：

- "3B 小模型在明确切好的子任务里，通过 SFT 或 DPO，能比 base 更稳定或更像客服"

这个叙事更真实，也更经得起深入追问。

## 5. 回顾性改进建议

- 更早把任务拆成 `SFT` 和 `DPO` 两条线，而不是混着试
- 更早把高风险场景从"证明模型有用"里拿掉
- 更早把 stronger judge 和 hard gate 做起来
- 更早把 case-level routing 作为主指标，而不是均分

## 6. 简历里可写的表述

### 版本 A：偏结果

- 设计并迭代电商客服小模型对齐方案，将训练目标拆分为 `SFT 流程能力修复` 与 `DPO 客服偏好校准` 两条链路，在 targeted benchmark 上实现局部场景优于 base 的稳定提升。

### 版本 B：偏工程方法

- 重构电商客服 LLM 评测与迭代流程，引入 `failure-first` 选样、hard gate、stronger judge、case-level routing 和 manual review 策略，避免用全局平均分误判小模型对齐收益。

### 版本 C：偏具体成果

- 在 `failure-first` benchmark 中将 SFT 模型平均分从 base 的 `0.4531` 提升到 `0.7156`，4 个目标场景中 3 个优于 base；在真实客服偏好 benchmark 中将 DPO 模型平均分提升至 `0.5595`，5 个场景中 3 个优于 base，同时保留高风险场景的人工复核路由。

## 7. 核心工程判断力

如果只能强调一个核心判断力，建议关注以下这点：

> 项目最终的价值不在于证明模型有多强，而在于明确了什么场景该交给哪个模型、什么场景必须人工兜底，以及什么 benchmark 结论是可以相信的。

这比单纯报一串分数更能体现高级工程判断。
